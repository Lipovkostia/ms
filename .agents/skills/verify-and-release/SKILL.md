# Проверка и публикация

## Когда применять

Исправление ошибки, завершение функции, подготовка сайта к просмотру и публикация. Применяйте пропорционально задаче; сообщите пользователю кратко.

## До изменений

Изучите git status, инструкции проекта и журнал ошибки. Не считайте отредактированную строку доказательством исправления. Определите минимальный воспроизводимый сценарий и сохраняйте прежние файлы и данные пользователя.

## Проверки

- Для этого приложения используйте `.venv/bin/python -m unittest discover -s tests -v`. Проверяйте, что тесты действительно выполнились; сохраняйте код завершения. Не скрывайте неудачи перенаправлением или фильтрацией вывода.
- При изменении зависимостей сверяйте requirements.txt с импортами и используйте `.venv/bin/python -m pip check`. При ошибке отсутствующей зависимости проверяйте запуск именно без неё либо установку в чистом окружении, а не только своё окружение с уже установленным пакетом.
- Через Streamlit AppTest проверяйте основной сценарий: открытие раздела, поиск, выбор клиента, создание и редактирование задачи, черновик, пустой источник и неудачное обновление. AppTest не подтверждает внешний вид.
- Если доступны инструменты браузера или Playwright, откройте реально работающий сервер, проверьте консоль и основной сценарий, снимите экран ноутбука и мобильный экран, оцените переполнение и кликабельность. Не предполагайте, что браузер установлен; сначала проверьте доступные средства. Не добавляйте тяжёлые браузерные зависимости к runtime приложения ради одной проверки.
- Сервер должен успешно стартовать, отвечать на health-запрос и выполнять функциональный сценарий. Открытый порт сам по себе не подтверждает работу приложения. Не завершайте чужой процесс при конфликте порта.
- Реальный API проверяйте только при наличии действующего разрешения и реквизитов. Используйте чтение и выводите только безопасные диагностические счётчики. Проверка с подставленным ответом не является проверкой реальной интеграции.
- Для изменений только инструкций проверьте ссылки, команды, YAML front matter, область действия и `git diff --check`; не запускайте все тесты приложения без причины.

## Публикация

1. Убедитесь, что публикация входит в поручение пользователя. Этот скилл не предоставляет самостоятельного разрешения на будущие публикации или отправку сообщений.
2. Проверьте diff и отсутствие секретов, временных файлов, локальных баз и реальных клиентских данных. Зафиксируйте только нужные изменения.
3. Проверьте удалённую ветку и сохраните чужие изменения. Не используйте force push или сброс чужой работы. В этой облачной среде `git fetch origin main` обновляет FETCH_HEAD: сравнивайте и его, а не только origin/main.
4. Отправьте изменения разрешённым способом и подтвердите удалённый SHA. Не утверждайте, что отправка удалась, пока нет результата.
5. Если есть доступ к хостингу, дождитесь сборки и проверьте опубликованный сценарий. Если доступа нет, сообщите отдельно: GitHub обновлён, публичное развёртывание не проверено. Для Streamlit Cloud актуальные поля: ветка main, файл app.py; при устаревших зависимостях Manage app → Reboot app.

## Итог

Кратко сообщите результат, важные изменения, выполненные проверки и ссылку пользователя, если она подтверждена. Различайте локальную работу, отправку в GitHub, автоматическое развёртывание и фактическую проверку сайта. Не называйте отсутствующие проверки успешными. Не оставляйте пользователя с обещанием, что позже вы что-то проверите: закончите разрешённую работу или укажите конкретный внешний блокер.
