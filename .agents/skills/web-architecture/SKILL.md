# Архитектура веб-приложения

## Когда применять

Новая функция, подключение API, изменение модели данных, авторизация, синхронизация или устранение системной ошибки. Коротко сообщите о применении скилла.

## Основные действия

1. Проверьте структуру репозитория, действующие инструкции, зависимости и существующий путь данных. Определите источник истины и границы задачи. Не переписывайте исправные части без необходимости.
2. Разделите интерфейс, расчёты, правила, API-адаптеры и хранение. В этом проекте используйте существующие sales_center/analytics.py, recommendations.py, live_data.py, moysklad.py, storage.py, sync.py и providers.py. Формулы остаются чистыми и проверяемыми независимо от UI и AI.
3. Зафиксируйте контракт внешнего ответа: обязательные поля, nullable-поля, единицы денежных сумм, даты, пагинация, ограничения и отсутствие данных. Ноль, неизвестное значение и пустая коллекция не взаимозаменяемы. Не угадывайте названия эндпоинтов; сверяйте с официальной документацией.
4. Для загрузки используйте тайм-ауты, ограниченное число повторов временных ошибок и ограниченную параллельность. Не повторяйте автоматически необратимые действия без механизма идемпотентности. Полностью проверьте новый снимок до замены старого; при сбое сохраняйте последний успех.
5. Укажите жизненный цикл: где живёт ключ, где данные, что сохраняется после закрытия вкладки, что исчезает при перезапуске и когда происходит обновление. Таймер браузерной сессии не называть фоновым сервисом или реальным временем.
6. Изолируйте записи по серверно определённым аккаунту и пользователю. Проверяйте права не только при чтении, но и при обновлении записи. Поле выбора сотрудника в UI не заменяет авторизацию. Сохраняйте старые данные при миграциях; не присваивайте анонимные записи произвольному пользователю.
7. Подключайте зависимости по необходимости. Стандартная SQLite не требует ORM. Опциональный драйвер не должен ломать запуск всего приложения, когда соответствующая интеграция не настроена. Для настроенной, но недоступной функции покажите конкретную инструкцию; не подменяйте её фиктивным успехом.
8. Закройте основной пользовательский сценарий и ошибки. Если внешние ключи отсутствуют, реализуйте адаптер, конфигурацию и проверки подставленных ответов, затем точно обозначьте, что реальный доступ не проверен. Не требуйте внешних реквизитов до завершения независимой работы.

## Безопасность и точность

Ключи не сохранять в Git или тексте ошибок. Использовать HTTPS с проверкой TLS, параметризованные запросы и фиксированные разрешённые адреса API. Не логировать тела с клиентскими данными. Перед передачей клиентских фактов внешней AI-модели использовать явное согласие и минимальный набор данных. Проверка API-ключа не означает, что сообщения принимаются и отправляются.

## Проверки по риску

Финансовые расчёты, права доступа, изоляцию сотрудников, сохранение и восстановление после ошибки проверять осмысленными тестами. Для обратимой косметической правки не писать тест, повторяющий реализацию. Не вводить микросервисы, очереди или новый фронтенд без подтверждённой потребности.

В итоге кратко объяснить конечное поведение, изменённые границы архитектуры, выполненные проверки и внешние условия, которые действительно остаются необходимыми.
